# CMS: минимальный следующий этап

Дата: 25 ноября 2026. Статус: план и подготовка данных; CMS ещё не установлена.

## Что есть сейчас

`arr_site_v2/design-concept` — самостоятельный HTML/CSS/JS-прототип. Дизайн,
мобильная версия и взаимодействия готовы для дальнейшей разработки.
`arr_site_v2/cms` пока пустая. Старый React/Vite-сайт не является новой витриной:
упоминание его в предыдущем исследовании описывало прежний вариант интеграции.

Минимальное изменение сегодня: пять проектов и три сцены первого экрана вынесены
из `app.js` в `design-concept/content/projects.js`. Прототип импортирует их как
ES-модуль. Дизайн и пути к фотографиям сохранены. Это исходные данные для будущего
импорта, а не админка. Остальные тексты главной пока находятся в HTML.

## Выбранное направление

Payload CMS + PostgreSQL. CMS хранит контент и предоставляет API; витрина получает
свои данные через отдельный адаптер. Внутренние документы Payload не должны
распространяться по компонентам сайта. Для запуска публичной версии рекомендуем
Next.js с серверными/предварительно созданными страницами проектов. Это заменит
нынешние адреса `#project/...` на `/projects/...` и даст отдельные HTML, заголовки
и превью для каждого кейса. Перенос верстки в компоненты — отдельная работа.

Начать с одного развёртываемого приложения Next.js + Payload, без микросервисов.
Логически отделить публичные страницы, CMS-конфигурацию и адаптер контента.
PostgreSQL хранит записи, объектное S3-совместимое хранилище — изображения в production.
Локальная папка допустима для первого запуска разработки, но не для нескольких серверов.
Не выбирать хостинг и не оплачивать инфраструктуру на этом этапе.

## Первый рабочий срез CMS

1. Создать приложение в `arr_site_v2/cms`, зафиксировать совместимые версии и lockfile.
   Запустить локальную PostgreSQL; секреты только в окружении, `.env.example` без значений.
2. Добавить Users (вход администратора), Media (фото, alt), Projects (см. поля ниже).
   Регистрации для посетителей нет. Изменение контента доступно только сотруднику.
3. Включить черновики и версии. Публичные запросы возвращают только опубликованные
   записи. Проверить это напрямую через API, включая запросы версий и черновиков.
4. Импортировать пять текущих проектов как черновики и существующие фото, повторный
   запуск импорта не должен создавать дубликаты. Проверить авторские описания и годы.
5. Подключить один опубликованный проект к витрине через адаптер. Проверить сценарий:
   вход → изменение заголовка/обложки → черновик → публикация → обновление сайта.

Критерий окончания этапа: пользователь может поменять один проект в настоящей
админке и увидеть опубликованный результат без правки исходников. Сейчас этот
критерий ещё не выполнен.

## Модель контента

Projects: стабильный `legacyId` для импорта; уникальный slug; title; category
(sport/culture/business); year; short; description; cover (связь с Media);
gallery (упорядоченный список связей и подписей); sortOrder; встроенный статус
публикации Payload. Существующие `id` сохранить как legacyId, не использовать
как внутренние идентификаторы базы. `label` вычислять по category.

Media: файл, alt, подпись, размеры и варианты изображений. Условия доступа к
оригиналам определить до публичной загрузки: черновик проекта сам по себе не
делает связанный файл приватным. На первом этапе использовать только фотографии,
допущенные к публичному показу.

Следом: глобальные настройки главной (заголовки, сцены, порядок избранных проектов),
контакты, SEO. Зарегистрированный логотип оставить защищённым бренд-ресурсом;
не предлагать редактору свободно менять его цвета или пропорции.

## Что обеспечивает возможность роста

- Смена дизайна затрагивает компоненты и стили, а проекты и медиа остаются в CMS.
- Изменение модели проходит через версионируемые миграции, резервную копию и проверку
  восстановления. Для переименования/удаления полей нужен перенос данных.
- При росте посещаемости: кеш страниц и CDN для фото; публикация сбрасывает кеш
  затронутых страниц. Не запрашивать CMS на каждое движение пользователя.
- При росте каталога: серверная пагинация, индексы по slug/category/статусу/порядку,
  отдельные запросы галерей вместо загрузки всего каталога сразу.
- Адаптер преобразует CMS-документы в данные витрины; смена CMS всё равно потребует
  миграции и нового адаптера, но не переписывания каждого компонента.
- До подключения редакторского ввода заменить текущие шаблоны innerHTML безопасным
  выводом текста/атрибутов и проверкой URL. Rich text отображать штатным renderer.

Текущий прототип не проверялся нагрузкой и не является production-архитектурой.
Он загружает весь небольшой каталог и использует клиентскую hash-навигацию.
Это нормально для утверждения дизайна, но не основа большого каталога без доработок.

## Не включать в первый этап

CRM, заявки, роли со сложными согласованиями, универсальный конструктор страниц,
мультиязычность и массовую загрузку архива. Сначала довести публикацию одного кейса.
